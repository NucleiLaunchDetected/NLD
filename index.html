1. 문제 인식 및 설계 목표

"오픈소스 화이트박스 환경에서 AI가 취약점을 잘 찾으려면 어떤 조건이 필요한가? 또한 토큰을 최대한 아끼면서 취약점을 찾기 위해서 어떻게 해야 할까?" 에 대한 고민을 시작으로 프로젝트를 진행하였습니다.

핵심 설계 결정: 왜 이 구조인가?

  • 토큰 절감 — diff 기반, 함수 단위 분석
    전체 오픈소스 프로젝트를 input으로 주기에는 토큰 부담이 너무 큼. 오픈소스 취약점이 가장 많이 나오는 시점은 릴리즈 패치 직후임 → 이전/신규 릴리즈 태그 diff에서 변경된 함수만 추출, 분석 scope를 최소화
  • 컨텍스트 정제 — 전체 소스 무작정 주는 것 금지
    CPG(Code Property Graph) MCP 툴로 필요한 흐름만 읽도록 함, 또한 tree-sitter, rg, ctags를 통해 코드만 on-demand로 읽도록 구성 → LLM이 필요한 증거만 정확히 가져오게 제어
  • 지식 강화 — diff 기반 RAG 활용
    기존 CVE 패치 함수들을 LLM으로 추상화한 지식 DB 구성, diff 함수와 코드적으로 유사한 것끼리 매핑해 취약점 유형 힌트 제공
  • 프롬프트 설계 — 분석 순서 지정, 추측 금지, 일관된 판정
    AGENTS.md로 역할·탐지 scope·분석 룰·Broad→Strict 2-pass를 명시, important 항목으로 추측 금지, reject 이유 학습 누적
목표 1
  • 릴리즈 diff 함수 기반 취약점 탐지
  • 토큰 최소화 + 신규 패치에서 취약점 발견
목표 2
  • MCP 기반 RAG · CPG로 에이전트 문맥 강화
  • LLM이 필요한 정보만 on-demand 수집
목표 3
  • 현재는 C/C++ 대상 memory corruption류 취약점을 우선적으로 탐지
  • 이후 다른 logic bug 등 취약점 탐지 기능 확장 예정

2. 시스템 개요

robocat는 오픈소스 C/C++/PHP의 버전 간 diff를 분석하여 취약점을 자동 탐지·검증하고 CVE 보고서 초안을 생성하는 종합 정적 분석 파이프라인입니다.

ℹ️
프로젝트 한 줄 정의 RAG·CPG를 결합한 MCP 기반 LLM Agent — 오픈소스 릴리즈 diff 기반 함수 단위 취약점 탐지
⚡
Dual-Pass 분석 원칙 모든 분석은 Broad Candidate Discovery(광범위 후보 수집) → Strict Confirmation(엄격 확인) 2단계를 거침. 최종 보고서 strict_results의 status=confirmed 항목만 CVE 신청 대상.

3. 컴포넌트 상세

[A] Orchestration Layer

run_target_pipeline.shShell
  • 전체 파이프라인 진입점 — 아래 B~C 단계를 순차 구동
  • 필수: --target · --repo · --old · --new
  • 선택: --language(기본 c) · --joern-port · --candidate-k
  • 자동 생성: configs/<target>.json, diff 아티팩트, retriever 결과

[B] Release Diff 추출

💡
왜 릴리즈 diff 함수 단위인가? 오픈소스 취약점은 릴리즈 패치 직후에 가장 많이 발견되기 때문, 전체 소스 대신 변경된 함수를 기준으로 분석해 토큰 부담을 대폭 감소시킴.
c_extractor.py1차
  • 입력: 로컬 git repo 경로, old/new 태그
  • git diff → 변경된 함수만 파싱·추출
  • 출력: diff_functions.json, diff.txt
generate_diff_retriever.py2차
  • 입력: diff_functions.json
  • purpose / function_summary / full_code 필드 구성
  • 출력: diff_retriever.json

[C] RAG 구성

CVE 패치 데이터에서 추출한 취약점 지식 DB를 기반으로, diff 함수와 코드적으로 유사한 과거 취약점 유형을 LLM에 힌트로 제공합니다.

📚
RAG 지식 구축 과정 CVEfixes DB에서 취약점 원인이 된 함수 단위 패치 → LLM으로 자연어 추상화 (NVD · Exploit-DB · GitHub CVE 설명 참고) → purpose / function_summary / vulnerability_behavior 등 구조화된 지식으로 저장

[F] MCP Server

Claude/Codex 에이전트가 취약점 분석 시 실시간 호출하는 MCP(Model Context Protocol) 서버. 에이전트가 subprocess로 띄우고 stdio로 통신합니다.

⚡
왜 MCP인가? LLM이 외부 도구를 자유롭게 연결·활용 가능. 소스코드 전체를 context에 넣는 대신, 필요한 CPG 쿼리 결과와 코드 스니펫만 on-demand로 가져와 컨텍스트를 정제함.

CPG 쿼리 내부 흐름

  1. 1CPG revision 계산 — git HEAD hash 또는 config 파일 SHA-1
  2. 2Redis 캐시 조회 — 동일 쿼리 결과 존재 시 Joern 우회, 즉시 반환
  3. 3캐시 미스 시: TaintQueryBuilder / CallContextQueryBuilder로 Scala 쿼리 생성 → import_cpg.scala 헤더 prepend
  4. 4Joern REST /query-sync에 POST → JSON 응답 수신 (callgraph + ossdataflow 오버레이 적용)
  5. 5결과 Redis에 저장 → 에이전트에 반환

[G] Claude / Codex Agent (Analysis Layer)

AGENTS.md 프로토콜에 따라 동작하는 AI 에이전트. CPG 1차 분석 → 소스코드 직접 검증 2차 순으로, 불일치 시 소스코드 우선.

권장 MCP 툴 호출 순서 (7단계)

  1. 1check_cpg_status — Joern workspace 정상 여부 확인
  2. 2get_retrieved_knowledge — RAG 예측 취약점 유형 힌트 (가설로만 사용)
  3. 3get_cpg_summary — 대상 함수 시그니처, caller/callee 확정
  4. 4find_dataflow — attacker-controlled source → memory sink 경로 확인
  5. 5find_sanitizer_or_guard — guard/sanitizer가 sink를 지배하는지 확인
  6. 6map_vuln_context — 로컬 위험 연산(크기/인덱스/alloc-free-use) 수집
  7. 7read_source_context / read_definition / find_references — 최종 코드 사실 검증용, 필요한 문맥만 슬라이스해서 확인

증거 신뢰도 기준

신뢰도조건
Highattacker-controlled source → memory sink 경로 확인 + guard 부재/불충분
Medium경로 일부만 확인되었으나 코드상 위험 연산이 명확
Low / Rejectsource 불명확, 경로 불명확, 방어코드가 지배함 / examples·tests 경로만 존재

6. 프롬프트 설계 전략

AGENTS.md 핵심 설계 원칙

  • 역할 지정 — 메모리 커럽션 전문 취약점 분석가 (이후에는 다른 취약점 유형마다 역할을 다르게 지정할 예정)
  • 탐지 Scope 제한 — diff 변경 함수 위주 분석, 불필요한 코드 탐색 금지
  • 분석 순서 강제 — 7단계 MCP 툴 호출 순서로 일관된 답변 보장
  • Broad → Strict 2-pass — 광범위 후보 수집 후 엄격 확인, Pass 2에서 신규 추가 금지
  • 추측 금지 (IMPORTANT) — 불확실하면 Strict에서 보고 금지, 코드 사실만 기반
  • Reject 이유 학습 누적 — library-only trigger path 등 패턴 축적
  • CPG vs source 불일치 처리 — CPG 결과와 소스 다르면 소스 우선

실제 Codex 실행 User 프롬프트
